React DayPicker already knows how to animate a month change, it just ships
without a look. When the month changes it clones the old month, pins the clone
over the new one with `position: absolute`, clips both with `overflow: hidden`
and adds a class to each: an *exit* class on the clone's weeks and caption, an
*enter* class on the new ones. GodUI fills those class names with the shared
`godui-slide-*` and `godui-fade-*` keyframes.

Going forward, the old weeks get `weeks_before_exit` (they slide out to the
left) and the new ones `weeks_after_enter` (in from the right). The slide
distance is a whole month, `--godui-enter-distance: 100%` of the weeks' own
width, and RTL flips its sign.

The two halves share one duration and one curve. The shared tokens give the
enter a spring and the exit `ease-out-expo`, which leaves faster than the new
month arrives and opens a gap between them. Redefining `--ease-out-expo` on the
weeks puts both on the spring, so the old month's right edge and the new
month's left edge stay together for the whole slide. Only `translate` and
`opacity` change.

These overrides sit on the calendar's root, aimed at the
`data-animated-weeks` elements React DayPicker marks, not in `classNames.weeks`.
A `classNames` key you pass replaces GodUI's string for that key, so timing
kept there would vanish with your own `weeks` styles.

>

React DayPicker removes the clone, and strips the enter classes from the new
month, when the old *caption* fires `animationend`. Whatever the weeks are
doing at that moment gets cut. The shared fade-out lasts 150ms and the slide
260ms, so out of the box the old month would vanish mid-slide.

GodUI stretches the caption's fade-out to the slide's duration, and shortens
the new weeks' enter to the same 260ms, so all four animations end on the same
frame and the cleanup removes a clone that's already gone.

Two more details come from React DayPicker. It adds these classes with
`classList.add`, which throws on a value containing a space, so every class
name is a single class and the overrides are set separately, from the root. And a second click while the month is sliding changes the month without
starting a second slide, so the clone never stacks.

>

The day you pick dips to 88% and springs back on `ease-spring-bouncy`. The fill
itself snaps.

A day only pops when it *becomes* selected while it's on screen. Each day
button remembers whether it was filled on its first render and compares during
render, so a calendar that loads with a date selected doesn't pop, and neither
does a selected day in a month you navigate back to, because React DayPicker
mounts that month's days fresh. In a range only the two ends pop; the middle
fills without moving.

The month clone copies the attribute along with the rest of the DOM, so the
pop is switched off inside it, or the clone would replay it as it slides away.
And the button's own press scale is turned off on day cells: two animations on
`scale` at once and Chrome composites neither.

## Why GPU-only

The weeks animate `translate` and `opacity`, the caption `opacity`, the picked
day `scale`. React DayPicker writes `position` and `overflow` once when a slide
starts and clears them once when it ends; nothing in between needs layout. A
month with one more week makes the calendar a row taller at once.

## Reduced motion

`--godui-motion: 0` cancels the slide distance and the dip, so the months
cross-fade in 150ms and the picked day fills without moving.
