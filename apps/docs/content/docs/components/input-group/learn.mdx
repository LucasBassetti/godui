When the field inside the group gets focus, the ring fades in and grows from
98% to full size in 150ms on `ease-out-expo`, so most of the change lands in
the first few frames. The border colour snaps in the same frame, which keeps
the focused state readable before the ring has finished.

The scene runs at 800ms. On the left is a plain Input, whose ring snaps
because an `<input>` can't hold a `::before`. On the right is the Input
Group.

<LearnChapter
  label="Box-shadow vs a pseudo-element"
  scene={<AutoPlayScene label="Box-shadow vs a pseudo-element" demo="focus-ring-slow" />}
  code={`// shadcn: the ring is the group's own box-shadow
"transition-[color,box-shadow]
 has-[…:focus-visible]:ring-[3px]
 has-[…:focus-visible]:ring-ring/50"

// GodUI: the same box-shadow, on a layer
"before:pointer-events-none before:absolute
 before:-inset-px before:rounded-[inherit]
 before:ring-[3px] before:ring-ring/50"`}
>

shadcn's ring is a 3px `box-shadow` on the group, and fading a shadow means
repainting it every frame. GodUI draws the same shadow on a `::before` and
fades the layer instead.

The layer has to line up exactly. It is `absolute`, and absolute insets are
measured from inside the border, so `-inset-px` pushes it out by the group's
1px border to cover the border box, the box shadcn's shadow starts from.
`rounded-[inherit]` copies the group's radius, so the 3px spread curves
concentrically with the border, even on a pill-shaped group. Once focused,
the two rings match pixel for pixel.

`pointer-events-none` lets clicks pass through the layer to addon buttons.
The invalid state only swaps the layer's ring colour to `destructive`.

## Why GPU-only

Only the `::before` layer's `opacity` and `scale` change, which the
compositor handles without repainting the shadow. The border colour snaps
instead of transitioning, as it would cost a repaint for every frame.

## Reduced motion

`motion-reduce:before:transition-none` removes the transition: the ring
appears and disappears at full size in one frame.
