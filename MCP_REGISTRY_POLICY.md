# GodUI MCP registry policy

This policy covers the catalog consumed by `@godui/mcp` and the MCP
configuration generated by `@godui/cli`.

## Decision

The default registry remains live and freshness-first. A new MCP process reads
the current catalog from `https://godui.design/r`; it does not require an MCP
package update when a component is released. The client caches successful
index and component responses only in memory for that process. It has no
persistent stale-data fallback: network failures, malformed metadata, and a
configured revision mismatch fail the request.

Freshness and reproducibility are separate modes. The live URL is mutable and
does not promise that two processes see the same catalog. Consumers that need a
reproducible catalog must use a commit-addressed or otherwise immutable
snapshot URL and set `GODUI_REGISTRY_REVISION` to the revision published in its
`index.json`.

## Requirements

### Registry content

- The registry is generated from the version-controlled root `registry.json`
  and the docs category metadata in a reviewed source revision.
- Every published `index.json` must include that source/deployment `revision`.
  The index and component files must be built and deployed as one revision; an
  immutable snapshot must never be overwritten. Deployment timestamps belong
  in the release record rather than in the generated payload, so the same
  registry inputs can be rebuilt byte-for-byte.
- A pinned client rejects an index whose revision is missing or different from
  `GODUI_REGISTRY_REVISION`. An unpinned client may use the live endpoint for
  freshness, but consumers must treat its content as changing input.
- The default endpoint must use HTTPS. Endpoint overrides are a trust boundary
  for development, private mirrors, and pinned snapshots; they are not a
  signature or sandbox.

### Integrity and provenance

- Registry changes are audited through the source revision, pull request, CI
  build, deployment record, and the generated index metadata.
- MCP releases use immutable npm versions and npm trusted publishing
  provenance (`pnpm publish --provenance`). A published version is never
  replaced; a fix gets a new version.
- The CLI and manual examples pin the generated runtime to the approved
  `@godui/mcp@0.1.0` release. Updating that pin requires a reviewed MCP release
  and a new CLI release. The `@godui/cli@latest` command is only a bootstrap
  convenience; for an audited setup, pin the CLI invocation too (for example,
  `npx @godui/cli@0.1.0 install cursor`). The persisted IDE configuration
  contains the exact MCP version.
- The current registry protocol provides HTTPS transport and revision
  provenance, not a detached cryptographic signature over registry content.
  Until signed metadata is introduced, high-assurance consumers must retain a
  snapshot URL and independently recorded SHA-256 digests for the files they
  approve. A future signed-manifest mode must verify the manifest before
  serving any catalog data and fail closed on signature, digest, or key errors.

### Rollback

- Keep the last known-good immutable registry snapshot and the corresponding
  MCP package version in the release record.
- To recover from a bad live deployment, restore the previous deployment or
  start the server with the previous snapshot URL and its revision pin, then
  restart the MCP process. The process-local cache is deliberately not a
  rollback store.
- Rollbacks must not repoint an existing npm version or overwrite an immutable
  snapshot. Record the incident, affected source revision, restored revision,
  package version, and verification result.

## Audit record

For each registry or MCP release, retain:

- source and registry revisions;
- the deployed registry base URL and deployment timestamp;
- the exact `@godui/mcp` and CLI versions;
- npm package integrity/provenance information; and
- approved snapshot file digests when reproducibility or rollback is required.

This gives the live product path the freshness it needs while giving audited
consumers an explicit, verifiable path to reproduce or roll back a catalog.
